Network

What the app does and doesn't control.

The container always listens on 0.0.0.0:3825 internally — that's set by the Dockerfile and isn't editable from the UI. The public address is decided by the orchestrator (Coolify domain config, the ports: line in docker-compose.yml, or your reverse proxy). Only two fields below take effect at runtime:

FieldWhat it doesExample
Public base URLThe URL users hit in their browser. Used in verification emails, OIDC redirect URIs, and Discord notifications. Set this before turning on email or SSO.https://app.vitriol.rocks
Allowed originOptional Host-header lock. If set, requests with any other Host return 403. Defense-in-depth behind a misconfigured proxy. Leave blank in dev.app.vitriol.rocks
Public base URL must match what users type in the browser, including the scheme. If users reach you via https:// but you set http://, OAuth callbacks will silently fail and verification email links will go to the wrong scheme.

Sign-up & format toggles

Allow self sign-up

When on, the sign-in page shows a "Create an account" link. New accounts are created with the role you pick below.

Default role on sign-up

  • Viewer — read-only. They see the UI but can't run conversions. They can request access from their profile.
  • Pending — locked-out screen until an admin approves. Sends notifications to admins via email + Discord.
  • User — full conversion access immediately (no approval).
Recommended: Pending if you have working SMTP + Discord, otherwise Viewer so users at least land somewhere usable.

Disabled input / output formats

Comma-separated extension list (with leading dot). Disabled formats won't appear in the UI dropdown and will be rejected at the API.

.exe,.iso,.dmg
SMTP (verification + admin notifications)

Required for email verification, password resets, and pending-approval notifications. Without SMTP, sign-ups still work but users won't receive verification mail and the email_verified_at flag will never be set.

Common providers

Purelymail

  1. Sign in to purelymail.com and make sure the address you want to send from is configured under your domain.
  2. Open Account Settings → SMTP / IMAP and copy the SMTP password (this is separate from your account password — generate one here).
  3. Use these settings:
Host:     smtp.purelymail.com
Port:     587
User:     support@yourdomain
Password: SMTP password from Purelymail settings
From:     support@yourdomain
STARTTLS: ✓

Purelymail also supports implicit TLS on port 465. If you prefer that, set Port to 465 and uncheck STARTTLS.

Gmail (personal account)

  1. Enable 2-step verification on your Google account.
  2. Visit myaccount.google.com/apppasswords and create an "App password" (16 random characters).
  3. Use these settings:
Host:     smtp.gmail.com
Port:     587
User:     you@gmail.com
Password: app-password-from-step-2
From:     you@gmail.com
STARTTLS: ✓

SendGrid

Host:     smtp.sendgrid.net
Port:     587
User:     apikey
Password: SG.xxxxxxxx (your SendGrid API key)
From:     noreply@yourdomain
STARTTLS: ✓

Mailgun

Host:     smtp.mailgun.org
Port:     587
User:     postmaster@mg.yourdomain
Password: SMTP password from Mailgun dashboard
From:     noreply@yourdomain
STARTTLS: ✓

Amazon SES

Host:     email-smtp.us-east-1.amazonaws.com
Port:     587
User:     SMTP username from SES → SMTP credentials
Password: SMTP password (different from your AWS secret key)
From:     noreply@yourdomain
STARTTLS: ✓
From address must be a domain you've verified with the provider, or mail will be rejected by recipient servers. Gmail is the exception — your account email is fine.
Discord webhook

Sends a notification when someone signs up as Pending or a Viewer requests access.

  1. In your Discord server: Server Settings → Integrations → Webhooks → New Webhook.
  2. Pick the channel notifications should land in.
  3. Click Copy Webhook URL — it looks like: 
    https://discord.com/api/webhooks/123456789012345678/long-token
  4. Paste it into the Discord webhook URL field. Save.

Test it: have someone sign up with self-signup set to "Pending". The channel should get a message within a second or two.

SSO providers — Google & GitHub

Google

  1. Open console.cloud.google.com, create or pick a project.
  2. APIs & Services → OAuth consent screen. Pick External, fill in app name, support email, developer email. Add the email and profile scopes.
  3. Credentials → Create credentials → OAuth client ID → Web application.
  4. Authorized redirect URI: 
    YOUR_PUBLIC_BASE_URL/api/v1/auth/sso/google/callback
  5. Save. Copy the Client ID and Client secret into the matching fields. Save settings.

GitHub

  1. GitHub: Settings → Developer settings → OAuth Apps → New OAuth App.
  2. Fill in: 
    Application name:    Vitriol
Homepage URL:        YOUR_PUBLIC_BASE_URL
Authorization URL:   YOUR_PUBLIC_BASE_URL/api/v1/auth/sso/github/callback
  3. Click Register application, then Generate a new client secret.
  4. Copy the Client ID and the just-generated secret into the form. Save.
The buttons on the sign-in page are rendered only for providers that have both a client ID and a secret saved. Until both are set, that provider stays hidden — no need to disable anything.
OpenID Connect — Authentik / Keycloak / Auth0 / Okta / Zitadel

One generic OIDC slot. As long as your IdP serves a valid .well-known/openid-configuration document, it works. The server form shows the absolute redirect URI on page load — register that with your IdP first.

Common redirect URI to register:

YOUR_PUBLIC_BASE_URL/api/v1/auth/sso/oidc/callback

Authentik

  1. Admin interface → Applications → Providers → Create.
  2. Pick OAuth2/OpenID Provider. Name it vitriol.
  3. Authorization flow: default-provider-authorization-implicit-consent (or explicit).
  4. Client type: Confidential. Authentik will generate the client ID + secret — note them.
  5. Redirect URIs: paste the URI above.
  6. Signing key: pick the default RS256 key.
  7. Save the provider.
  8. Applications → Create. Slug vitriol, link to the provider.
  9. Back in Vitriol, fill in: 
    Display name:  Authentik
Issuer URL:    https://authentik.example.com/application/o/vitriol/
Client ID:     from step 4
Client secret: from step 4
Scopes:        openid email profile
  10. Tick Enable OIDC sign-in, save.

Keycloak

  1. Pick / create a realm.
  2. Clients → Create client. Type: OpenID Connect. Client ID: vitriol.
  3. Client authentication: On (so Keycloak issues a secret).
  4. Valid redirect URIs: paste the URI above.
  5. Save. Open the Credentials tab → copy the secret.
  6. In Vitriol: 
    Issuer URL:    https://keycloak.example.com/realms/your-realm
Client ID:     vitriol
Client secret: from credentials tab

Auth0

  1. Auth0 dashboard → Applications → Create Application → Regular Web Application.
  2. Settings tab → Allowed Callback URLs: paste the URI above.
  3. Copy Domain, Client ID, and Client Secret.
  4. In Vitriol: 
    Issuer URL:    https://your-tenant.auth0.com/
Client ID:     from Auth0
Client secret: from Auth0

Okta

  1. Okta admin → Applications → Create App Integration → OIDC – Web Application.
  2. Sign-in redirect URIs: paste the URI above.
  3. Copy Client ID and Client secret from the General tab.
  4. In Vitriol, issuer URL is your Okta org domain: 
    Issuer URL:    https://your-org.okta.com
The Issuer URL field accepts either form — bare (https://idp/realms/x) or with the suffix (.../.well-known/openid-configuration). Vitriol normalizes it on save.
SSL cert pull

Vitriol itself doesn't terminate TLS — front it with a reverse proxy (Caddy / Traefik / Nginx). The cert-pull feature fetches renewed certs and drops them into /data/certs/fullchain.pem + /data/certs/privkey.pem for the proxy to pick up. Two modes cover anything you'd want to wire up.

Auto-renewal

The Auto-renew every N days field tells the background scheduler to re-run the pull on that interval. 0 disables auto-renewal — the operator pulls on demand via the Pull certs now button. Typical values: 7 for safety-margin renewal of 90-day Let's Encrypt certs, 30 for longer-lived certs.

Mode 1: Webhook

Vitriol makes an HTTP request to your cert API and parses JSON out of the response. Supports GET or POST and either static-header auth (X-Api-Key & friends) or HMAC body signing.

Fields

  • Webhook URL — your cert endpoint.
  • HTTP method — GET (most cert APIs) or POST.
  • Auth header name / value — set both for static-header auth (e.g. X-Api-Key). Takes precedence over HMAC.
  • HMAC shared secret — POST-only. Sent as X-Vitriol-Signature: sha256=<hex>.
  • Response cert / key fields — JSON keys to extract. Default fullchain / privkey; SphereSSL uses certPem / certKey.

Example — Vitriol's own format

POST your-webhook-url
Content-Type: application/json
X-Vitriol-Signature: sha256=<hmac of body using shared secret>

{"action": "pull-certs"}

→ Response:
{
  "fullchain": "-----BEGIN CERTIFICATE-----\n...\n",
  "privkey":   "-----BEGIN PRIVATE KEY-----\n...\n"
}

Example — SphereSSL

Mode:                  Webhook
Webhook URL:           https://spheressl.example.com/api/cert/your.host
HTTP method:           GET
Auth header name:      X-Api-Key
Auth header value:     your-spheressl-api-key
Response cert field:   certPem
Response key field:    certKey
Auto-renew every:      7 days

Mode 2: Script

Sometimes the cert API doesn't fit a clean GET/JSON shape — multi-step flows, custom auth, file-based outputs. Mode 2 runs a shell script you paste in. The container has bash, curl, and jq pre-installed; the script gets $VITRIOL_CERT_DIR pointing at /data/certs/ and is expected to write fullchain.pem and privkey.pem there.

Example — SphereSSL via script

#!/usr/bin/env bash
set -euo pipefail

API_KEY='your-spheressl-api-key'
DOMAIN='your.host'
URL="https://spheressl.example.com/api/cert/$DOMAIN"

RESPONSE=$(curl -fsSL -H "X-Api-Key: $API_KEY" "$URL")
echo "$RESPONSE" | jq -r .certPem > "$VITRIOL_CERT_DIR/fullchain.pem"
echo "$RESPONSE" | jq -r .certKey > "$VITRIOL_CERT_DIR/privkey.pem"

Exit code: 0 = success. Anything else marks the run as failed and surfaces stderr's last line in the UI status pill. 5-minute hard timeout. Runs as the container's non-root vitriol user, so sudo / apt-get won't work — you can curl, jq, write files under /data/, and call other HTTP services from within the container's network.

Tiny Flask example (Vitriol's native webhook format)

import hmac, hashlib
from flask import Flask, request, jsonify, abort

SECRET = b"same-shared-secret"
app = Flask(__name__)

@app.post("/pull-certs")
def pull():
    sig = request.headers.get("X-Vitriol-Signature", "")
    expected = "sha256=" + hmac.new(SECRET, request.data, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(sig, expected):
        abort(401)
    return jsonify(
        fullchain=open("/etc/letsencrypt/live/your.host/fullchain.pem").read(),
        privkey=open("/etc/letsencrypt/live/your.host/privkey.pem").read(),
    )

Trigger a pull manually with the Pull certs now button on the settings page, or from the API:

POST /api/v1/server/refresh-certs
Self-compile defaults

Whether each role can produce self-extracting .py or .exe outputs by default. Per-user grants in the Users tab override these.

  • Super admin can self-compile — usually leave on. The super admin always has Stone access regardless.
  • Admins can self-compile — turn off if you want self-compile to be an explicit per-user grant rather than implied by the admin role.
Self-compile produces native .exe output that runs your input file when executed. There's no malware-pipeline path (.py↔.exe is blocked at the engine level), but the resulting file can still be misused. Treat self-compile as a privileged capability — don't grant it to untrusted users.
