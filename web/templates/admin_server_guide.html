Conventions used throughout the UI:

  • A green ✓ saved badge next to a secret field means the column has a value stored at rest. Leave the field blank on Save to keep the existing value; only fill it in when you want to replace it.
  • Section headers with a green configured / active pill mean the integration is currently usable. Amber untested means credentials are saved but no test has run. Red last test failed means the most recent probe got an error — open the section to see why.
  • Every section is accordion-style: only one is open at a time. Save settings persists every change made across all sections, not just the open one.

Network

What the app does and doesn't control.

The container always listens on 0.0.0.0:3825 internally — that's set by the Dockerfile and isn't editable from the UI. The public address is decided by the orchestrator (Coolify domain config, the ports: line in docker-compose.yml, or your reverse proxy). Only one field below takes effect at runtime:

FieldWhat it doesExample
Public base URLThe URL users hit in their browser. Used in verification emails, SSO redirect URIs, and notification messages. Set this before turning on email or SSO.https://app.vitriol.rocks
Public base URL must match what users type in the browser, including the scheme. If users reach you via https:// but you set http://, OAuth callbacks will silently fail and verification email links will go to the wrong scheme.

Sign-up

Allow self sign-up

When on, the sign-in page shows a "Create an account" link. New accounts come in with the role you pick below. The same toggle also gates new SSO sign-ups — without it, only operators-added accounts can sign in via SSO.

Default role on sign-up

  • Viewer — read-only. They see the UI but can't run conversions. They can request access from their profile.
  • Pending — locked-out screen until an admin approves. Sends notifications to admins via email + any enabled notification webhooks.
  • User — full conversion access immediately (no approval).
  • Any custom role you've created from the Users tab also appears in this dropdown.
Recommended: Pending if you have working SMTP + a notification webhook, otherwise Viewer so users at least land somewhere usable.

Require email verification on sign-up

When on (default), new users are created with status=unverified and don't show up in the admin user list until they click the link in the verification email. Unverified rows auto-purge after 24 hours. When off, accounts are accepted immediately — useful for SMTP-less or closed-network deployments.

Username/password sign-in enabled

Master toggle. When off, the password form on /signin + /signup is hidden and the API returns 403 for password sign-ins — users can only get in via SSO. Safety net: the super admin can always sign in with a password regardless of this setting (so a broken IdP can't lock the operator out), and the UI refuses to let you turn it off unless at least one SSO provider is enabled and configured.

Disabled formats

Block specific input or output formats by file extension. Three tiers cascade — global is hardest, user is softest.

TierEffect
GloballyNobody can use these — including super admin. Hardest block.
Admin + belowSuper admin can still use; anyone with admin role or lower is blocked.
User + belowUsers / viewers / pending are blocked; admin and super admin can still use.

Each cell takes a comma-separated extension list with leading dots. Disabled formats are hidden from the conversion dropdown and rejected at the API.

Disabled inputs   Globally:        .exe,.dmg
                  Admin + below:   .bat
                  User + below:    (empty)
Disabled outputs  Globally:        .exe
                  Admin + below:   .py
                  User + below:    .exe,.py

A format only needs to be disabled at the strictest level you want it to apply — admins automatically inherit user-level blocks unless they're super admin.

SMTP (verification + admin notifications)

Required for email verification, password resets, and pending-approval notifications. Without SMTP, sign-ups still work but users won't receive verification mail.

SMTP enabled

Master toggle. Uncheck to pause outbound email without clearing credentials — useful for maintenance windows or when migrating providers. The ✓ saved badge next to the password field tells you whether the column has a value stored at rest, regardless of whether the toggle is on.

Testing

The Send test email button sends a one-off to whatever address you type in the field next to it (or the From address if you leave it blank). Errors include the exception class — SMTPAuthenticationError (535) for wrong credentials, SMTPConnectTimeoutError for network/firewall, SMTPResponseException (421) for rate-limited or blocked IPs. The section header pill flips to green configured after a successful test.

Notification webhooks

Multi-channel fan-out for admin alerts (new pending user, viewer access requests, etc.). Click + Add channel to pick a kind from the catalog. Eight kinds shipped; every enabled channel receives a copy of every notification.

Each row in the table has an inline enable toggle, a "last test" pill, and an Edit button that opens the per-kind form. Inside the edit form, a Test button sends a one-off "Vitriol — test notification." to the configured destination so you can verify the round-trip before relying on it for real alerts.

Discord

  1. In your Discord server: Server Settings → Integrations → Webhooks → New Webhook.
  2. Pick the channel notifications should land in, copy the webhook URL.
  3. Vitriol → + Add channel → Discord, paste the URL.

Slack

  1. Slack → Apps → Incoming Webhooks → Add to Slack, pick the channel, copy the webhook URL.
  2. Vitriol → + Add channel → Slack, paste the URL.

ntfy

Public ntfy.sh or self-hosted server. Fields:

  • Server URL — e.g. https://ntfy.sh or your self-host URL.
  • Topic — e.g. vitriol-alerts. Anything subscribed to that topic will see the message.
  • Auth — pick None (public topic), Bearer token, or Basic auth. For Basic, use the format user:pass in the token field.

Gotify

Self-hosted push server. From the Gotify UI, Apps → Create App, copy the per-app token. Paste server URL + token into the Vitriol form.

Telegram

  1. Talk to @BotFather on Telegram, run /newbot, follow the prompts. Save the bot token.
  2. Start a chat with your new bot (so it can message you). To find your chat ID, visit https://api.telegram.org/bot<token>/getUpdates after sending the bot a message — your numeric chat ID is in the JSON.
  3. Vitriol → + Add channel → Telegram, paste the bot token and chat ID.

Generic webhook

Any HTTP endpoint that accepts a request. Useful for self-built notification routers, internal tooling, or anything not on this list.

  • URL, Method (POST/PUT/PATCH), Headers (JSON object), Body template with {message} placeholder.
  • Bearer token (optional) — added as Authorization: Bearer ... header automatically.

Script

Runs bash -c "<your script>" inside the container. The notification text is in $VITRIOL_MESSAGE. 15-second hard timeout. Useful for sending via curl with custom flow control, or for triggering local-only tooling.

#!/usr/bin/env bash
curl -fsSL \
  --data-urlencode "text=$VITRIOL_MESSAGE" \
  https://your.api/notify

Bluesky

Posts to the AT Protocol via app password — generate one at bsky.app/settings/app-passwords (don't use your real account password). 280-character cap; longer messages are truncated.

Server URL defaults to https://bsky.social but you can point at a self-hosted PDS.

Signal and Twitter/X aren't shipped — Signal needs a signal-cli sidecar service, and X's API requires a paid tier plus OAuth 2.0 user-context auth. Both are doable additions; ask if you need them.
SSO providers — Google & GitHub

Each provider has an enabled toggle (pause without clearing credentials), a client ID + client secret field, a Test button, and a last-test stamp next to the button. The Test button opens the full OAuth round-trip in a popup; on success it lands on a "Test passed" page showing the IdP's reported sub, email, and name without creating a user account or signing you in.

  4. Authorized JavaScript origins: YOUR_PUBLIC_BASE_URL
  5. Authorized redirect URI: 
    YOUR_PUBLIC_BASE_URL/api/v1/auth/sso/google/callback

GitHub

  1. GitHub: Settings → Developer settings → OAuth Apps → New OAuth App.
  2. Fill in: 
    Application name:    Vitriol
Homepage URL:        YOUR_PUBLIC_BASE_URL

Buttons on the sign-in page are rendered only for providers that are enabled AND have both client ID + secret saved. Disabling a provider hides its button without clearing credentials.
OpenID Connect providers

Add as many OIDC providers as you need — Authentik for staff, Auth0 for customers, Okta for partners. Each gets its own row in the table and its own button on the sign-in page. Click + Add OIDC provider to open the catalog with 11 prefilled templates plus a Custom OIDC option for anything not on the list.

Templates shipped

Authentik · Keycloak · Auth0 · Okta · Microsoft Entra ID (Azure AD) · Google Identity Platform · GitLab · Amazon Cognito · Sign in with Apple · ZITADEL · Salesforce · Custom OIDC

Each template pre-fills the issuer URL pattern with placeholders, sets sensible default scopes, and (for Authentik) enables the auto-provisioning section so you can wire that up at the same time. You replace placeholders with your real values, paste in your client_id and client_secret, and save.

Each row's slug becomes a URL fragment

Vitriol's callback URL for an OIDC row with slug authentik is:

YOUR_PUBLIC_BASE_URL/api/v1/auth/sso/authentik/callback

Register that exact URL in your IdP's allowed redirect URIs. The edit form previews the absolute URL based on your Public base URL setting.

Inline row controls

  • Enable toggle — flips the button on/off in real time without opening the edit form.
  • Test button — opens the SSO popup with ?test=1. On success, the row's last-test pill updates to ok <timestamp>.
  • Edit — full configuration including the optional User Provisioning section.

Authentik

  1. Authentik admin → Applications → Create with wizard. Slug vitriol.
  2. Pick OAuth2/OpenID Provider. Authorization flow: default-provider-authorization-implicit-consent (or explicit).
  3. Client type: Confidential. Note the auto-generated client ID + secret.
  4. Redirect URIs: paste the URL above (with your actual slug).
  5. Vitriol → + Add OIDC provider → Authentik card. Replace <your-domain> and <app-slug> in the issuer URL, paste client ID + secret.

Authentik auto-provisioning (optional)

Inside the Authentik provider's edit dialog, the User provisioning section can auto-create approved Vitriol users in Authentik so the first "Continue with Authentik" click works without you pre-creating each user by hand. Setup:

  1. Authentik admin → Directory → Tokens → New token.
  2. Identifier: any (e.g. vitriol-provisioning). User: a service account in the Admin group.
  3. Copy the generated key. In Vitriol's OIDC edit form, paste it into IdP admin API token.
  4. Check Auto-provision approved users into this IdP. Save.
  5. From now on, when an admin approves a pending user in Vitriol, Vitriol POSTs {username, email, name, is_active: true} to Authentik's /api/v3/core/users/ — the user lands in Authentik's directory with no password set. They use Authentik's password-recovery flow to set their own.

Per-provider provisioning failures don't block the approval — Vitriol's audit log flags failed provisions so the admin can manually create the IdP-side account if needed.

Server secret key

The signing key for session tokens (JWT) and the encryption key (via PBKDF2 → Fernet) for every secret stored at rest — SMTP password, OAuth secrets, OIDC client secrets, IdP API tokens. Vitriol generates one automatically on first boot.

Where it's stored

Two locations, in priority order:

  1. Environment variable — set SECRET_KEY (or VITRIOL_SECRET_KEY) in your orchestrator. Wins over everything else. Optional.
  2. /data/.secret_key file — auto-created on first boot.
  3. Database fallback — also auto-mirrored into the vitriol.db file. If the dotfile is ever lost (volume hiccup, Coolify cache cleanup, etc.) Vitriol restores the key from the DB so encrypted secrets stay decryptable.

Set the env var only if you want bullet-proof deterministic behaviour across bare-metal restores / volume rebuilds. The dual-storage fallback covers normal operation including container restarts and Docker volume hiccups.

Reveal / copy

The Reveal button decrypts and displays the current key — useful when you want to copy it into the env var or a settings export. The Copy button puts it on the clipboard.

Regenerate

Rotates the key safely: decrypts every encrypted column with the old key, generates a fresh key, re-encrypts everything with the new key, persists the new key to file + DB, restarts the container. All active sessions are invalidated (everyone signs in again).

Don't regenerate while an encrypted column can't be decrypted with the current key (rare — happens after a manual volume restore from a different deployment). The rotation refuses to run in that state and surfaces an error telling you which field to re-enter first.
SSL cert pull

Vitriol itself doesn't terminate TLS — front it with a reverse proxy (Caddy / Traefik / Nginx). The cert-pull feature fetches renewed certs and drops them into /data/certs/fullchain.pem + /data/certs/privkey.pem for the proxy to pick up. Two modes cover anything you'd want to wire up.

Auto-renewal

The Auto-renew every N days field tells the background scheduler to re-run the pull on that interval. 0 disables auto-renewal — the operator pulls on demand via the Pull certs now button. Typical values: 7 for safety-margin renewal of 90-day Let's Encrypt certs, 30 for longer-lived certs.

Mode 1: Webhook

Vitriol makes an HTTP request to your cert API and parses JSON out of the response. Supports GET or POST and either static-header auth (X-Api-Key & friends) or HMAC body signing.

Fields

  • Webhook URL — your cert endpoint.
  • HTTP method — GET (most cert APIs) or POST.
  • Auth header name / value — set both for static-header auth (e.g. X-Api-Key). Takes precedence over HMAC.
  • HMAC shared secret — POST-only. Sent as X-Vitriol-Signature: sha256=<hex>.
  • Response cert / key fields — JSON keys to extract. Default fullchain / privkey; SphereSSL uses certPem / certKey.

Example — Vitriol's own format

POST your-webhook-url
Content-Type: application/json
X-Vitriol-Signature: sha256=<hmac of body using shared secret>

{"action": "pull-certs"}

→ Response:
{
  "fullchain": "-----BEGIN CERTIFICATE-----\n...\n",
  "privkey":   "-----BEGIN PRIVATE KEY-----\n...\n"
}

Example — SphereSSL

Mode:                  Webhook
Webhook URL:           https://spheressl.example.com/api/cert/your.host
HTTP method:           GET
Auth header name:      X-Api-Key
Auth header value:     your-spheressl-api-key
Response cert field:   certPem
Response key field:    certKey
Auto-renew every:      7 days

Mode 2: Script

Sometimes the cert API doesn't fit a clean GET/JSON shape — multi-step flows, custom auth, file-based outputs. Mode 2 runs a shell script you paste in. The container has bash, curl, and jq pre-installed; the script gets $VITRIOL_CERT_DIR pointing at /data/certs/ and is expected to write fullchain.pem and privkey.pem there.

Example — SphereSSL via script

#!/usr/bin/env bash
set -euo pipefail

API_KEY='your-spheressl-api-key'
DOMAIN='your.host'
URL="https://spheressl.example.com/api/cert/$DOMAIN"

RESPONSE=$(curl -fsSL -H "X-Api-Key: $API_KEY" "$URL")
echo "$RESPONSE" | jq -r .certPem > "$VITRIOL_CERT_DIR/fullchain.pem"
echo "$RESPONSE" | jq -r .certKey > "$VITRIOL_CERT_DIR/privkey.pem"

Exit code: 0 = success. Anything else marks the run as failed and surfaces stderr's last line in the UI status pill. 5-minute hard timeout. Runs as the container's non-root vitriol user, so sudo / apt-get won't work — you can curl, jq, write files under /data/, and call other HTTP services from within the container's network.

Trigger a pull manually with the Pull certs now button on the settings page, or from the API:

POST /api/v1/server/refresh-certs
Output retention (per role)

How long converted output files stay in /data/outputs/ before being cleaned up. The cleanup task runs every 30 minutes and applies the per-role policy below. Same units (minutes / hours / days) per row.

FieldEffect
Max filesKeep at most N most-recent done files per user in this role. 0 = unlimited count.
Max ageDelete files older than this. 0 = no time-based cleanup.
Unitminutes / hours / days — applies to Max age.
Delete on downloadRemove the file from disk immediately after the user successfully downloads it, regardless of count/age limits. Useful for one-shot transient outputs.

Default policy:

Super admin: 0 files, 0 age          — unlimited
Admin:       0 files, 30 days        — unlimited count, 30-day age
User:        20 files, 24 hours      — strictest tier
Retention deletes the file on disk; the job row stays in the database for audit purposes. Files removed by cleanup don't appear in the Files tab.
Self-compile defaults

Whether each role can produce self-extracting .py or .exe outputs by default. Per-user grants in the Users tab override these.

  • Super admin can self-compile — usually leave on. The super admin always has Stone access regardless.
  • Admins can self-compile — turn off if you want self-compile to be an explicit per-user grant rather than implied by the admin role.
Self-compile produces a native .exe output that runs your input file when executed. There's no malware-pipeline path (.py↔.exe is blocked at the engine level), but the resulting file can still be misused. Treat self-compile as a privileged capability — don't grant it to untrusted users.
Export / import settings

Export bundles your server config — limits, SMTP, OAuth, OIDC providers, custom roles, retention, cert-pull, notification channels — into a single JSON file you can store, version-control, or restore on another install.

Export options

  • Encrypt with a password — checked: file is PBKDF2-derived + Fernet-encrypted. Unchecked: file contains your secrets in plaintext, so treat it like a private key.
  • Hash — every export embeds a SHA-256 of the canonical payload, so import detects tampering. The hash is generated server-side and isn't user-editable.

Import flow

  1. Pick a settings file. Vitriol verifies the format header.
  2. If encrypted, prompts for the export password.
  3. Shows a confirmation page summarizing what's about to be applied (with counts of OIDC providers / custom roles / notification channels).
  4. Apply — overwrites existing values. Existing OIDC rows / custom roles / notification channels with matching slugs/names are replaced; others are left alone.
Importing an unencrypted file replaces all secrets with the plaintext values it contains. Don't import an export that was generated against a different SECRET_KEY without re-pasting secrets afterward — the encrypted blobs in the file are valid only against the originating instance's key.
Roles & permissions

Vitriol has five built-in roles + an unlimited number of operator-defined custom roles that overlay a built-in role's ceiling. Roles are managed from the Users tab (under Manage roles), not here in Server settings — but understanding them is important for picking the right default-on-sign-up role above.

Built-in roles

RoleCan doNotes
super_admin Everything. Restart server, edit server settings, manage all users including admins, view + delete everyone's files, full conversion access. Exactly one row in the DB always has this role. Cannot be deleted, demoted, or banned by any HTTP path. Password sign-in stays enabled for super admin even when the master toggle is off (recovery escape hatch).
admin Manage users below admin (suspend / ban / grant Stone / grant self-compile / approve pending). View server tab. Run conversions with Stone and self-compile by default. Can't edit server settings, create or delete admins, or touch the super admin. Subject to the daily/rate caps under Limits.
user Run conversions, manage own profile + API keys, view own files. Stone and self-compile only if granted per-user. The standard "real user" role.
pending See the "Awaiting approval" screen and sign out. Nothing else. Used as the default on sign-up when you want manual approval. Notifications fire to admins (email + every enabled notification webhook) on transition to pending.
viewer Read-only — see the UI but can't run conversions. Request access from profile. Useful for "demo viewer" accounts or trial users.

Custom roles

Custom roles are an overlay on top of a built-in role. They share the built-in's ceiling for capabilities the operator hasn't explicitly opted into — i.e. a custom role with base_role = user can never have admin capabilities, even if you check every box.

Creating a custom role

  1. Users tab → Manage roles → New role.
  2. Pick a name (free text, e.g. Power user, Beta tester).
  3. Pick a base role — this is the ceiling. Capabilities checked on this custom role only take effect if the base role would have allowed them.
  4. Toggle the individual capabilities you want granted on top of the base.
  5. Save.

Assigning a custom role to a user

  1. Users tab → click the user row → Edit.
  2. Pick from the Custom role dropdown (or leave blank to use the bare built-in role).
  3. Save. The user's effective capability set immediately uses the custom-role overlay; their base role stays the same so role-based queries ("all admins") keep working.

Custom role on sign-up

In Sign-up's default-role dropdown, your custom roles appear alongside the built-ins. Pick one to assign new self-sign-ups to it automatically. The base role is aligned server-side based on the custom role's ceiling.

Capability changes apply immediately to every user assigned to the custom role — there's no per-user invalidation step. Changing a role from "admin ceiling" to "user ceiling" instantly demotes everyone wearing that role; they'll see the new effective role on next page render.

Per-user grants

Two grants live on the user row, independent of role: Stone enabled and self-compile enabled. These are admin-toggleable from the Users tab and override whatever the user's role would otherwise allow. Useful for "this one User-role account can also use Stone" without spinning up a new custom role.

Approval flow

When a user signs up with default role = Pending:

  1. Vitriol creates the row with status = unverified (if email verification is on) or active (if off).
  2. On email verification (or immediately, if verification is off): an ApprovalRequest row is created and notifications fire to every admin/super-admin email + every enabled notification webhook.
  3. Admin clicks Approve in the Users tab → picks the target role from a dropdown → confirms.
  4. If any OIDC provider has Auto-provision approved users enabled, Vitriol pushes the new user into the IdP at this moment.
  5. User can now sign in.
